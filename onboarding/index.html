Onboarding

Backpressure, sin cajas negras

Reconstruyendo, pieza por pieza, los mecanismos detrás de un incidente típico de congestión de colas.

Este proyecto reconstruye, pieza por pieza y sin cajas negras, los mecanismos que cualquier backend con una cola de mensajes, un cliente HTTP y un pool de workers puede combinar para terminar en un incidente de congestión de colas. En vez de levantar un stack completo (una API, una base de datos, un worker asíncrono, un downstream lento) y ver el síntoma final sin entender el porqué, cada script numerado aísla un solo concepto con RabbitMQ y Python puro, y lo prueba con una demo reproducible y con asserts.

La idea de "avanzar de a uno" no es solo de presentación: es literalmente cómo está diseñado el código. 01 y 02 establecen cómo RabbitMQ entrega y confirma mensajes. 03 le pone un límite a cuánto puede acaparar un consumer. Ahí el proyecto se despega de RabbitMQ por completo y se mete al cliente HTTP: 04 y 05 muestran cómo un timeout mal configurado disfraza el agotamiento de un pool de conexiones como si fuera "el downstream que tardó". 06 agrega la pieza de resiliencia que corta el tráfico hacia un downstream que ya se sabe que está caído. El paso 07 es donde todo esto se junta: un semáforo de aplicación ocupando un "slot" mientras un consumer de RabbitMQ llama al cliente HTTP lento — el mecanismo completo de "queued sube, in_flight tope en N", el patrón detrás de la mayoría de las congestiones de cola en producción, sin importar el nombre del servicio en el que aparezcan.

Cada tarjeta trae el diagrama del mecanismo, la salida real del script paso a paso (revelada de a poco, con el estado relevante junto a cada línea) y el código completo como referencia — y una explicación que profundiza más allá del docstring, conectando cada mecanismo con su equivalente en Celery/producción y con el resto de los pasos.

RabbitMQ · fundamentos

Paso 1 · Connection, Channel, Queue

El viaje redondo más simple: publicar un mensaje y sacarlo de vuelta.

ConnectionChannelQueuebasic_publishbasic_get(auto_ack=True)

Por qué importa más adelante

Nada todavía directamente — pero cada mecanismo de congestión que se arma en los pasos siguientes (prefetch, acks, pool HTTP, circuit breaker) se apoya sobre esta base: una Connection pesada que se abre una vez, un Channel liviano que se usa para todo, y una Queue que es solo un buffer con reglas de entrega configurables.

Este paso no resuelve ningún problema del incidente todavía — establece el vocabulario que todos los pasos siguientes dan por sentado. Vale la pena quedarse un momento en las tres capas del modelo AMQP 0-9-1, porque cada una tiene un costo y un ciclo de vida distinto:

  • Connection es una conexión TCP real, con handshake y autenticación. Es cara de abrir (decenas de milisegundos, a veces más si hay TLS) y por eso en producción casi nunca se abre una por mensaje: se abre una vez por proceso worker y se reutiliza.
  • Channel es un canal lógico multiplexado dentro de esa misma conexión TCP — el mismo truco que streams en HTTP/2: muchas operaciones concurrentes, un solo socket. Es barato de abrir/cerrar comparado con una Connection, pero no es gratis ni thread-safe (ver la nota de pika más abajo).
  • Queue es el buffer real de mensajes. queue_declare es idempotente — declarar dos veces la misma cola con la misma configuración no hace nada — pero ojo: si no se pasa durable=True (como en este script, a propósito, para no complicar el primer paso), la cola vive solo en memoria y desaparece si RabbitMQ se reinicia.

El otro detalle fácil de pasar por alto: nunca se publica "directo a una cola". Todo basic_publish pasa por un exchange, que decide a qué cola(s) va el mensaje según su routing key. exchange="" es el default exchange, un exchange implícito de tipo direct que RabbitMQ pre-enlaza automáticamente a cada cola declarada, usando el nombre de la cola como routing key. Es el atajo que usa este repo entero (ningún paso planeado usa exchanges tipados fanout/direct/topic propios).

Por último, la diferencia entre basic_get (este paso) y basic_consume (paso 02) es la diferencia entre pull y push: basic_get es "dame un mensaje si hay, ahora, sin bloquear" — útil para scripts y debugging, pero nadie construye un worker real sobre basic_get en un loop porque desperdicia round-trips. Los consumers de verdad (incluido Celery/kombu por debajo) usan basic_consume.

import os

import pika

QUEUE_NAME = "step1_queue"

# Host/puerto configurables por variable de entorno para poder meter un
# proxy en medio (p.ej. mitmproxy) sin tocar el codigo.
RABBITMQ_HOST = os.environ.get("RABBITMQ_HOST", "localhost")
RABBITMQ_PORT = int(os.environ.get("RABBITMQ_PORT", "5672"))


def main():
    # 1. Abrir la connection (TCP + login) contra el RabbitMQ que levantamos
    #    con docker-compose. guest/guest son las credenciales por defecto de
    #    la imagen oficial, validas solo para conexiones locales.
    connection = pika.BlockingConnection(
        pika.ConnectionParameters(host=RABBITMQ_HOST, port=RABBITMQ_PORT)
    )
    print(f"Conexion abierta ({RABBITMQ_HOST}:{RABBITMQ_PORT}).")

    # 2. Abrir un channel sobre esa connection.
    channel = connection.channel()
    print("Channel abierto.")

    # 3. Declarar la cola (crearla si no existe).
    channel.queue_declare(queue=QUEUE_NAME)
    print(f"Cola '{QUEUE_NAME}' declarada.")

    # 4. Publicar un mensaje de prueba.
    #    exchange="" es el "default exchange" de RabbitMQ: un exchange
    #    implicito que enruta cada mensaje directo a la cola cuyo nombre
    #    coincide exactamente con routing_key. En realidad TODO publish pasa
    #    por un exchange (nunca se publica directo a una cola); usar "" es el
    #    atajo para "sin exchange propio, entrega por nombre de cola". Es lo
    #    mismo que usa el incidente real que reconstruimos (ver README de
    #    `_backup_original`), asi que todos los scripts numerados se quedan
    #    con "" -- no hay ningun paso planeado que use exchanges tipados
    #    (fanout/direct/topic).
    mensaje = "hola desde step1"
    channel.basic_publish(exchange="", routing_key=QUEUE_NAME, body=mensaje)
    print(f"Mensaje publicado: {mensaje!r}")

    # 5. Consumirlo de vuelta (basic_get = "dame un mensaje si hay, sin
    #    bloquear esperando"; distinto de basic_consume, que veremos despues).
    method_frame, header_frame, body = channel.basic_get(
        # auto_ack=True: apenas RabbitMQ nos entrega el mensaje lo da por
        # confirmado (ack) automaticamente y lo borra de la cola. Con
        # auto_ack=False el mensaje queda "entregado pero no confirmado": si
        # el consumidor se cae antes de mandar el ack explicito (channel.
        # basic_ack), RabbitMQ lo vuelve a poner en la cola para reintentar.
        # Aqui usamos True porque este script no hace nada que pueda fallar
        # entre recibir y procesar; el manejo real de acks (y sus riesgos:
        # duplicados, mensajes perdidos) lo vemos mas adelante.
        queue=QUEUE_NAME, auto_ack=True
    )
    if method_frame:
        print(f"Mensaje recibido de vuelta: {body.decode()!r}")
    else:
        print("No habia ningun mensaje en la cola (raro, algo fallo).")

    # 6. Cerrar prolijo.
    connection.close()
    print("Conexion cerrada.")


if __name__ == "__main__":
    main()

RabbitMQ · entrega y confirmación

Paso 2 · basic_consume + ack manual

«Entregado» y «confirmado» son dos momentos distintos — y esa brecha es donde vive Celery acks_late.

basic_consume (push)auto_ack=Falsebasic_ackredeliveryat-least-once

El hueco que deja acks_late

"mensaje-2" en la demo simula un worker que revienta después de recibir el trabajo pero antes de confirmarlo. Nadie reenvía nada explícitamente: RabbitMQ detecta el canal muerto con un mensaje unacked colgando y lo re-encola por su cuenta. Este es precisamente el mecanismo detrás de duplicados en sistemas con retries — y la razón por la que "procesar dos veces" tiene que ser seguro.

La idea central de este paso es una sola distinción, pero es la que sostiene todo el modelo de confiabilidad de RabbitMQ:

entregado (delivered) ≠ confirmado (acked)

Con auto_ack=False, en cuanto on_message se dispara el mensaje ya se marcó "unacked" — sigue existiendo en el servidor, ligado a ese canal específico, pero ya no cuenta como "listo para entregar" a otro consumer. Desde ahí hay exactamente tres finales posibles:

  • basic_ack → borrado permanente. El contrato se cumplió.
  • basic_nack(requeue=True) → vuelve a la cola de inmediato, disponible para cualquier consumer (incluido el mismo).
  • el canal o la conexión se cierran sin haber mandado ack (crash, kill -9, excepción no capturada que tumba el proceso) → RabbitMQ lo detecta y lo redelivera solo, sin que nadie se lo pida.

Ese tercer caso es, con otras palabras, exactamente lo que Celery implementa con task_acks_late=True: si el worker muere a mitad de una tarea, la tarea nunca se dio por completada y Rabbit la vuelve a poner en juego. Es una garantía at-least-once (al menos una vez), y viene con un precio: si el worker murió después de terminar el trabajo real pero antes de que el ack saliera por la red, esa tarea se reprocesa. Por eso cualquier tarea con acks_late=True tiene que ser idempotente si el efecto secundario importa — no es un detalle opcional, es la contraparte obligatoria de la garantía at-least-once.

El otro cambio de este paso, basic_get → basic_consume, no es cosmético: basic_consume no bloquea ni consume nada por sí solo, solo suscribe el canal. start_consuming() es la que de verdad entra a un loop bloqueante leyendo frames del socket — el mismo patrón que corre cualquier worker real en producción: nunca sabe cuántos mensajes van a llegar, solo se queda escuchando indefinidamente hasta que algo externo lo detenga.

import os

import pika

QUEUE_NAME = "step2_queue"

RABBITMQ_HOST = os.environ.get("RABBITMQ_HOST", "localhost")
RABBITMQ_PORT = int(os.environ.get("RABBITMQ_PORT", "5672"))


def connect():
    connection = pika.BlockingConnection(
        pika.ConnectionParameters(host=RABBITMQ_HOST, port=RABBITMQ_PORT)
    )
    channel = connection.channel()
    channel.queue_declare(queue=QUEUE_NAME)
    return connection, channel


def ronda_1():
    print("=== Ronda 1: publicar 3, ackear 2, dejar 1 sin ack a proposito ===")
    connection, channel = connect()

    for i in range(1, 4):
        channel.basic_publish(exchange="", routing_key=QUEUE_NAME, body=f"mensaje-{i}")
    print("3 mensajes publicados.")

    procesados = []

    # Este callback lo invoca pika UNA VEZ POR MENSAJE, no una sola vez con
    # los 3 juntos. Cada mensaje que RabbitMQ empuja dispara su propia
    # llamada a on_message, en orden (primero mensaje-1, luego mensaje-2,
    # luego mensaje-3).
    def on_message(ch, method_frame, header_frame, body):
        # Llegar hasta aqui es "entregado", nada mas -- RabbitMQ ya nos dio
        # el mensaje, pero todavia no se borro de verdad. Con auto_ack=False,
        # "entregado" y "consumido" (borrado permanente) son dos momentos
        # DISTINTOS: entregado pasa siempre que on_message se ejecuta;
        # consumido de verdad pasa recien en la linea de basic_ack de abajo
        # -- y si esa linea nunca se ejecuta (como con mensaje-2 aqui abajo),
        # el mensaje jamas se consume, aunque ya lo hayamos "recibido" e
        # impreso.
        texto = body.decode()
        print(f"Recibido: {texto!r} (delivery_tag={method_frame.delivery_tag})")

        if texto == "mensaje-2":
            # A proposito NO llamamos basic_ack. Simula un consumer que se
            # cae (crash, kill -9, excepcion no capturada) despues de recibir
            # el mensaje pero antes de confirmarlo -- el mismo hueco que
            # acks_late=True deja abierto en Celery.
            print("  -> simulando crash: NO se manda ack para este mensaje.")
        else:
            # AQUI es donde el mensaje se consume/borra de verdad -- no en
            # la linea de arriba donde lo "recibimos". mensaje-1 y mensaje-3
            # pasan por aqui; mensaje-2 nunca (ver el "if" de arriba), por
            # eso el unico que sobrevive para la ronda 2.
            ch.basic_ack(delivery_tag=method_frame.delivery_tag)
            print("  -> ack enviado.")

        procesados.append(texto)
        # stop_consuming() es la UNICA razon por la que start_consuming()
        # (mas abajo) no se queda escuchando para siempre. Sin este corte,
        # el script procesaria los 3 mensajes igual, pero despues se
        # quedaria bloqueado esperando un 4to mensaje que nunca llega -- asi
        # es como corre un worker de verdad en produccion: no sabe cuantos
        # mensajes van a llegar, simplemente se queda escuchando.
        if len(procesados) == 3:
            ch.stop_consuming()

    # basic_consume() NO consume nada por si solo: solo SUSCRIBE este canal
    # a la cola ("de ahora en adelante, empujame lo que llegue y avisame por
    # on_message"). Retorna casi al instante, no bloquea.
    channel.basic_consume(queue=QUEUE_NAME, on_message_callback=on_message, auto_ack=False)

    # start_consuming() es lo que de verdad bloquea: entra a un loop que lee
    # frames del socket y dispara on_message por cada uno, sin saber de
    # antemano cuantos van a llegar. Se queda "escuchando" indefinidamente
    # hasta que algo (aqui, el propio callback via stop_consuming()) le
    # diga que pare.
    channel.start_consuming()

    # Cerramos SIN haber ackeado "mensaje-2". Ese mensaje sigue en estado
    # "unacked" ligado a este canal; al cerrar la conexion, RabbitMQ lo
    # detecta y lo vuelve a poner en la cola para el proximo consumer.
    connection.close()
    print("Conexion de ronda 1 cerrada (mensaje-2 nunca fue ackeado).\n")


def ronda_2():
    print("=== Ronda 2: nueva conexion, ver que mensaje-2 reaparecio ===")
    connection, channel = connect()

    recibidos = []

    def on_message(ch, method_frame, header_frame, body):
        texto = body.decode()
        print(f"Recibido: {texto!r} (delivery_tag={method_frame.delivery_tag})")
        # Aqui SI se consume/borra de verdad "mensaje-2" -- la primera vez
        # (ronda_1) se entrego pero nunca se llego a este punto.
        ch.basic_ack(delivery_tag=method_frame.delivery_tag)
        print("  -> ack enviado (esta vez si).")
        recibidos.append(texto)
        # Igual que en ronda_1: sin este stop_consoming(), start_consuming()
        # de abajo se quedaria escuchando para siempre esperando otro
        # mensaje que nunca va a llegar (la cola solo tenia el 1 redeliverado).
        if len(recibidos) == 1:
            ch.stop_consuming()

    # basic_consume() solo suscribe (no bloquea); start_consuming() es el
    # que bloquea de verdad escuchando lo que llegue -- ver los comentarios
    # equivalentes en ronda_1() para el detalle completo.
    channel.basic_consume(queue=QUEUE_NAME, on_message_callback=on_message, auto_ack=False)
    channel.start_consuming()

    assert recibidos == ["mensaje-2"], (
        f"Se esperaba que solo 'mensaje-2' quedara pendiente, llego {recibidos}"
    )
    print("Confirmado: 'mensaje-2' fue redeliverado porque nunca se ackeo.")

    connection.close()
    print("Conexion de ronda 2 cerrada.")


def main():
    ronda_1()
    ronda_2()


if __name__ == "__main__":
    main()

RabbitMQ · control de flujo

Paso 3 · basic_qos(prefetch_count=N)

Cuántos mensajes sin confirmar puede tener un consumer a la vez — el equivalente exacto de worker_prefetch_multiplier.

basic_qosprefetch_countworker_prefetch_multiplierfairness vs throughput

Prefetch vs el semáforo del paso 07

prefetch_count lo hace cumplir RabbitMQ, a nivel de protocolo AMQP — controla cuántos mensajes le entrega al canal. El semáforo que se construirá en el paso 07 (WORKER_CONCURRENCY) lo hace cumplir nuestro propio código de aplicación — cuántas llamadas HTTP concurrentes se dejan correr. En Celery real ambos coinciden por diseño: prefetch_count = worker_prefetch_multiplier × concurrency.

Sin límite, RabbitMQ empuja mensajes a un consumer tan rápido como el socket lo permite, sin preguntar si ese consumer ya está ocupado — se acumulan del lado del cliente como "unacked", esperando turno de CPU/callback. basic_qos(prefetch_count=N) es la válvula que le dice al servidor: "no me entregues nada nuevo si ya tengo N sin confirmar".

Esto es, número por número, el mecanismo detrás de worker_prefetch_multiplier de Celery (default 4): el prefetch_count real que un worker Celery le pide a Rabbit es worker_prefetch_multiplier × --concurrency. Con los defaults y --concurrency=2, ese worker reserva 8 tareas sin confirmar aunque solo pueda correr 2 en paralelo — 6 quedan "en cola local", esperando turno, aunque hubiera 500 tareas más urgentes esperando en Rabbit que otro worker más libre podría tomar antes. Con multiplier=1 (lo que se prueba aquí, prefetch_count=1 por consumer), un worker nunca acapara más de lo que puede procesar ahora mismo.

La demo deja ver la diferencia entre dos preguntas que se confunden fácil: control de flujo no es lo mismo que balanceo de carga. Sin límite (escenario 1), el primer consumer suscrito se lleva todo de una sola vez — ni siquiera es que sea "más rápido", es que llegó primero y no había ningún límite que se lo impidiera. Con prefetch_count=1 (escenario 2), nadie puede acaparar más de un mensaje sin confirmar, pero el reparto final tampoco es 50/50: el worker rápido sigue terminando con la mayoría, porque en el 1 segundo que el worker lento tarda en soltar su único slot, el rápido ya tuvo tiempo de pedir y procesar varios más. Prefetch acota cuánto puede haber en vuelo, no decide a quién le toca.

Vale la pena anotar un detalle de la UI de RabbitMQ que confunde a cualquiera la primera vez: "Prefetch count: 0" en la pestaña Channels significa "ilimitado", no "cero mensajes".

import os
import threading
import time

import pika

QUEUE_NAME = "step3_queue"
NUM_MESSAGES = 10

RABBITMQ_HOST = os.environ.get("RABBITMQ_HOST", "localhost")
RABBITMQ_PORT = int(os.environ.get("RABBITMQ_PORT", "5672"))


def _connect():
    connection = pika.BlockingConnection(
        pika.ConnectionParameters(host=RABBITMQ_HOST, port=RABBITMQ_PORT)
    )
    channel = connection.channel()
    channel.queue_declare(queue=QUEUE_NAME)
    return connection, channel


def _purge():
    connection, channel = _connect()
    channel.queue_purge(queue=QUEUE_NAME)
    connection.close()


def _publish(n):
    connection, channel = _connect()
    for i in range(1, n + 1):
        channel.basic_publish(exchange="", routing_key=QUEUE_NAME, body=f"msg-{i}")
    connection.close()
    print(f"{n} mensajes publicados.")


def _worker(nombre, prefetch_count, sleep_seconds, procesados, total_esperado, deadline):
    """Corre en su propio hilo, con su propia connection (pika no es
    thread-safe: cada connection solo se puede usar desde el hilo que la
    creo)."""
    connection, channel = _connect()
    if prefetch_count is not None:
        channel.basic_qos(prefetch_count=prefetch_count)

    def on_message(ch, method_frame, header_frame, body):
        time.sleep(sleep_seconds)  # simula el "trabajo" de procesar el mensaje
        ch.basic_ack(delivery_tag=method_frame.delivery_tag)
        procesados[nombre].append(body.decode())
        print(f"  [{nombre}] proceso {body.decode()!r} (lleva {len(procesados[nombre])})")

    channel.basic_consume(queue=QUEUE_NAME, on_message_callback=on_message)

    # Loop manual (en vez de start_consuming) para poder parar cuando ya se
    # proceso todo lo esperado, sin bloquear para siempre.
    while time.monotonic() < deadline:
        if sum(len(v) for v in procesados.values()) >= total_esperado:
            break
        connection.process_data_events(time_limit=0.2)

    connection.close()

Cliente HTTP · timeouts

Paso 4 · Timeout bare-int vs httpx.Timeout partido

Un solo número para cuatro fases distintas — y por qué eso disfraza una espera de pool como si fuera un downstream lento.

httpx.Timeout(connect, read, write, pool)httpx.LimitsPoolTimeout

Ojo con el nombre repetido

pool= dentro de httpx.Timeout es un tiempo en segundos (cuánto esperar antes de rendirse). max_connections= dentro de httpx.Limits es una cantidad (cuántas conexiones simultáneas existen). Que ambos se llamen "pool" es solo nomenclatura de httpx, no una relación matemática entre los dos números.

Este es el primer paso que se aleja de RabbitMQ del todo — standalone, contra un servidor propio hecho con http.server que simplemente duerme y responde 200. El punto es aislar un solo mecanismo: qué significa realmente timeout= en httpx.

Cuando se pasa un número suelto (timeout=5), httpx lo expande por dentro a cuatro presupuestos independientes, todos iguales:

FaseQué mideAnalogía
connectEsperar el handshake TCPmarcar y que suene el teléfono
writeEsperar a mandar el body del requestterminar de hablar
readEsperar la respuesta ya conectadoesperar a que conteste ("el downstream tardó")
poolEsperar un slot libre del pool antes de intentar conectaresperar a que una línea del conmutador quede libre

httpx sí distingue las cuatro fases internamente — cada una tiene su propio reloj que arranca en cero al entrar a esa fase. El problema del bare-int no es que se pierda esa separación técnica; es que con un solo número no se le puede dar a pool un presupuesto corto (para fallar rápido si no hay conexiones libres) mientras se le da a read uno largo (para tolerar un downstream legítimamente lento). Si el número es lo bastante grande para lo segundo, automáticamente también lo es para lo primero — y entonces una espera larga de pool se disuelve, invisible, dentro del mismo margen que un read normal.

Con httpx.Timeout(pool=1, read=5, ...) (escenario B), la fase pool tiene su propio presupuesto corto: req-2 falla en ~1s con httpx.PoolTimeout explícito, sin haber tocado la red — una señal de tipo distinto (excepción, no solo duración), separada del presupuesto generoso que sigue protegiendo a un read lento legítimo.

Además de timeout, httpx.Limits tiene tres parámetros propios que también conviene no confundir entre sí:

ParámetroTipoQué controla
max_connectionscantidadtope de conexiones simultáneas — esto es lo que agota el pool
max_keepalive_connectionscantidadde las que ya terminaron, cuántas se guardan abiertas para reusar
keepalive_expirysegundoscuánto tiempo se mantiene abierta una conexión ociosa antes de cerrarla sola

En este script max_connections y max_keepalive_connections se pasan con el mismo número (1) solo para que no haya cierre/reapertura de conexión entre requests — no hace falta para el mecanismo de PoolTimeout en sí, que depende únicamente de max_connections. keepalive_expiry ni se toca: queda en su default de httpx (5.0s).

async def _timed_get(client, url, nombre):
    inicio = time.monotonic()
    try:
        resp = await client.get(url)
        elapsed = time.monotonic() - inicio
        print(f"  [{nombre}] OK status={resp.status_code} en {elapsed:.1f}s")
        return ("ok", elapsed)

async def escenario_bare_int(url):
    print(f"=== Escenario A: timeout={BARE_TIMEOUT} bare-int (mismo numero para connect/read/write/pool) ===")
    # max_connections=1: pool de una sola conexion a proposito, para que dos
    # requests concurrentes compitan de verdad por el mismo slot.
    limits = httpx.Limits(max_connections=1, max_keepalive_connections=1)

    # para ambas) -- de ahi en mas, quien consigue el unico slot del pool y
    # quien tiene que esperar ya depende del pool, no de esta linea.

El caveat honesto

En un worker Celery real esto casi no aplica: cada worker procesa una tarea a la vez, así que no hay "requests concurrentes del mismo proceso" compitiendo por el mismo pool de conexiones. Sigue valiendo la pena entenderlo porque sí aplica tal cual a cualquier servicio FastAPI/asyncio que atiende varias requests a la vez con asyncio.gather (o simplemente varias requests entrantes en paralelo) compartiendo un mismo httpx.AsyncClient — un patrón común en servicios backend con alta concurrencia.

El paso 04 probó que PoolTimeout existe con el caso mínimo (2 requests, 1 conexión). Este paso sube la escala a algo que se parece más a producción: POOL_SIZE=3 conexiones, N_REQUESTS=12 concurrentes — más requests que conexiones, así que se forman rondas. Con ceil(N/POOL) rondas, si nada fallara la ronda K empezaría recién en t=(K-1)×SLEEP_SECONDS y terminaría en t=K×SLEEP_SECONDS.

Con el timeout bare-int, cada fase reinicia su reloj al entrar — no es un presupuesto acumulado de principio a fin de todo el request. Eso significa que una ronda sobrevive mientras su propia espera de pool, sola, se mantenga por debajo del número configurado, sin importar cuánto hayan tardado las rondas anteriores.

Aquí es donde el disfraz se vuelve más peligroso que en el paso 04: el tipo de excepción ya es el correcto, PoolTimeout — pero viene marcado con el mismo número (5s) que tendría cualquier lectura lenta legítima si el downstream de verdad tardara 5 segundos en responder. Un log o una alerta que solo mira "elapsed≈5s, TimeoutException" no tiene forma de distinguir dos causas raíz completamente distintas: no había conexiones libres (se arregla con más max_connections) vs. el downstream está lento de verdad (se arregla en el downstream).

Con el presupuesto de pool separado y corto (escenario B), la distinción deja de depender de inspeccionar tipos de excepción con cuidado: se vuelve una cuestión de magnitud, visible a simple vista. La escala de tiempo misma de la falla ya dice "esto fue agotamiento de pool", sin necesidad de tocar para nada la paciencia que se le sigue dando a un downstream legítimamente lento.

async def _timed_get(client, url, nombre):
    inicio = time.monotonic()
    try:
        resp = await client.get(url)
        elapsed = time.monotonic() - inicio
        print(f"  [{nombre}] OK status={resp.status_code} en {elapsed:.1f}s")
        return ("ok", elapsed)

        elapsed = time.monotonic() - inicio
        print(f"  [{nombre}] {type(e).__name__} en {elapsed:.1f}s")

Resiliencia

Paso 6 · Circuit breaker: CLOSED / OPEN / HALF_OPEN

Un failure_threshold astronómico nunca protege a nadie -- deja de importar si el breaker existe.

can_execute / on_success / on_failurefailure_thresholdrecovery_timeoutfail fast

A quién protege el breaker

Es fácil pensar que el circuit breaker protege al downstream — y de rebote lo hace, dándole aire para recuperarse sin tráfico nuevo encima. Pero a quién protege directamente es al que llama: cada request cortado en OPEN se resuelve en microsegundos localmente, en vez de gastar el presupuesto entero de timeout (los pasos 04/05) contra un servicio que ya se sabe que va a fallar.

La máquina de tres estados es corta (menos de 30 líneas) pero vale la pena leerla con calma porque es el patrón exacto que usan implementaciones de producción como Hystrix o resilience4j, solo que simplificado a lo esencial:

  • CLOSED (estado inicial): deja pasar todo. Cada fallo suma failure_count; cualquier éxito lo resetea a 0 de inmediato.
  • OPEN: en cuanto failure_count >= failure_threshold. can_execute() devuelve False sin tocar la red — cero bytes hacia el downstream — hasta que pasen recovery_timeout segundos desde el último fallo.
  • HALF_OPEN: pasado ese tiempo, se deja pasar un request de prueba. Si sale bien, vuelta a CLOSED con el contador en 0; si sale mal, vuelve a sumar y puede reabrir.

El experimento de la demo es deliberadamente aburrido de leer y por eso es contundente: el único parámetro que cambia entre escenario A y B es failure_threshold (999999 vs 3) — ni el downstream, ni el cliente HTTP, ni la lógica de llamada cambian en absoluto. Con el umbral astronómico, el breaker existe en el código pero, en la práctica, es idéntico a no tener ninguno.

Un matiz importante para cuando esto se combine con retries/backoff más adelante: cada intento fallido dentro de un mismo request ya cuenta como su propio on_failure(). Por eso call_downstream() aquí hace un solo intento por llamada, sin retries: para ver exactamente qué hace el breaker por sí solo, sin ese segundo mecanismo mezclado.

También vale la pena notar qué es lo que este breaker no hace, comparado con implementaciones más sofisticadas: resetea failure_count a 0 con un solo on_success(), en vez de usar una ventana deslizante de tasa de error — el precio de la simplicidad de "contar fallos seguidos" en vez de "medir tasa de error en una ventana de tiempo".

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 1, recovery_timeout: int = 60):
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.failure_count = 0
        self.last_failure_time = 0
        self.state = "CLOSED"  # CLOSED, OPEN, HALF_OPEN

    def can_execute(self) -> bool:
        current_time = time.time()
        if self.state == "CLOSED":
            return True
        elif self.state == "OPEN":
            if current_time - self.last_failure_time >= self.recovery_timeout:
                self.state = "HALF_OPEN"
                return True
            return False
        else:  # HALF_OPEN
            return True

    def on_success(self):
        self.failure_count = 0
        self.state = "CLOSED"

    def on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = "OPEN"

def call_downstream(breaker, url):
    """Una sola llamada, sin retries -- ver el docstring del modulo sobre por
    que se deja afuera el loop de reintentos del original."""
    if not breaker.can_execute():
        return "short_circuited"

    try:
        with urllib.request.urlopen(url, timeout=5) as resp:
            status = resp.status
    except urllib.error.HTTPError as e:
        status = e.code

    if status >= 500:
        breaker.on_failure()
        return "downstream_error"

    breaker.on_success()
    return "ok"

Paso 7 · Worker slots (semaphore) + prefetch + HTTP lento

Donde todo lo anterior se junta: "queued sube, in_flight tope en N, queued baja de a N" -- el mecanismo real de la congestión.

WORKER_CONCURRENCYprefetch_count=1ack manual (acks_late)in_flight

WORKER_CONCURRENCY no es lo mismo que prefetch_count

Es fácil confundirlos porque los dos limitan "cuánto a la vez". prefetch_count (paso 03) es cuántos mensajes sin confirmar puede tener un solo consumer -- lo hace cumplir RabbitMQ. WORKER_CONCURRENCY es cuántos consumers existen en total -- eso lo decide nuestro propio código (acá, cuántos hilos lanzamos). En este paso cada worker usa prefetch_count=1 fijo; lo que cambia entre escenarios es cuántos workers hay, no su prefetch individual -- exactamente como Celery: worker_prefetch_multiplier=1 × --concurrency=N.

Los pasos 02 y 03 mostraron RabbitMQ por sí solo: basic_qos como válvula de entrega y basic_ack manual como confirmación. Los pasos 04-06 mostraron el cliente HTTP por sí solo: timeout partido, pool de conexiones, circuit breaker. Este paso no agrega ningún concepto nuevo del lado HTTP -- combina lo ya visto para mostrar el mecanismo que faltaba: qué pasa cuando cada mensaje ocupa un worker entero mientras dura la llamada downstream.

Cada uno de los WORKER_CONCURRENCY hilos es, a efectos prácticos, un "proceso Celery" con concurrency=1: su propia pika.BlockingConnection (pika no es thread-safe), su propio httpx.Client, y prefetch_count=1 -- nunca tiene más de un mensaje sin confirmar. El basic_ack se dispara recién después de que client.get() vuelve, no antes -- eso es task_acks_late=True: el mensaje sigue "en juego" (unacked, ocupando ese slot) durante toda la llamada lenta, no solo mientras Rabbit lo entrega.

Un loop de monitoreo en el hilo principal consulta queue_declare(passive=True).method.message_count cada ~0.3s -- eso cuenta mensajes Ready (todavía en la cola, nadie los tomó), no los que ya están unacked en manos de algún worker. Combinado con un contador local de in_flight, la salida en vivo muestra exactamente la frase del RUNBOOK.md: "queued sube, in_flight tope en N, queued baja de a N".

Con WORKER_CONCURRENCY=1 (Escenario A) el procesamiento es enteramente serial -- 12 mensajes, de a uno, sin importar que el downstream pudiera atender varios en paralelo. Con WORKER_CONCURRENCY=3 (Escenario B), in_flight sube hasta 3 y se queda ahí: 4 "rondas" de 3, el mismo patrón de rondas del paso 05, pero ahora la razón del límite no es un pool de HTTP -- es la cantidad de workers que decidimos lanzar.

(basic_qos(prefetch_count=1) + ack manual, pasos 02-03) llamando a un
downstream HTTP lento con el timeout partido bueno (leccion del paso 04):
nunca hay mas de N mensajes "in_flight" a la vez, sin importar cuantos queden
esperando (Ready) en la cola.

Como probar:

    docker compose up -d
    pip install -r requirements.txt   # ya incluye httpx
    python3 07_worker_slots.py
"""

import http.server
import os
import threading
import time

import httpx
import pika

QUEUE_NAME = "step7_queue"
SLEEP_SECONDS = float(os.environ.get("SLEEP_SECONDS", "1"))
N_MESSAGES = int(os.environ.get("N_MESSAGES", "12"))
WORKER_CONCURRENCY_A = int(os.environ.get("WORKER_CONCURRENCY_A", "1"))
WORKER_CONCURRENCY_B = int(os.environ.get("WORKER_CONCURRENCY_B", "3"))

RABBITMQ_HOST = os.environ.get("RABBITMQ_HOST", "localhost")
RABBITMQ_PORT = int(os.environ.get("RABBITMQ_PORT", "5672"))

# Timeout partido "bueno" (leccion del paso 04) -- no es el foco de este paso,
# solo evita que el HTTP client en si mismo sea la variable que confunde la
# demo. pool=1 no importa aca: cada worker usa su propio httpx.Client, un solo
# request a la vez, sin compartir pool con nadie (eso es el paso 05).
HTTP_TIMEOUT = httpx.Timeout(connect=2.0, read=5.0, write=5.0, pool=1.0)


class SlowHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        time.sleep(SLEEP_SECONDS)  # simula "el downstream tarda"
        body = b"ok"
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, format, *args):
        pass  # silenciar el log default de http.server, ensuciaria la demo


def start_server():
    server = http.server.ThreadingHTTPServer(("127.0.0.1", 0), SlowHandler)
    thread = threading.Thread(target=server.serve_forever, daemon=True)
    thread.start()
    return server


def _connect():
    connection = pika.BlockingConnection(
        pika.ConnectionParameters(host=RABBITMQ_HOST, port=RABBITMQ_PORT)
    )
    channel = connection.channel()
    channel.queue_declare(queue=QUEUE_NAME)
    return connection, channel


def _purge():
    connection, channel = _connect()
    channel.queue_purge(queue=QUEUE_NAME)
    connection.close()


def _publish(n):
    connection, channel = _connect()
    for i in range(1, n + 1):
        channel.basic_publish(exchange="", routing_key=QUEUE_NAME, body=f"msg-{i}")
    connection.close()
    print(f"{n} mensajes publicados.")


class InFlight:
    """Contador compartido entre los N hilos worker -- cuantos mensajes estan
    siendo procesados (unacked) en este instante, y el maximo que se alcanzo
    en toda la corrida."""

    def __init__(self):
        self._lock = threading.Lock()
        self._value = 0
        self.max_seen = 0

    def incr(self):
        with self._lock:
            self._value += 1
            self.max_seen = max(self.max_seen, self._value)
            return self._value

    def decr(self):
        with self._lock:
            self._value -= 1

    @property
    def value(self):
        with self._lock:
            return self._value


def _worker(worker_id, url, in_flight, procesados, total_esperado, deadline):
    """Un 'proceso Celery' con concurrency=1: su propia connection de pika
    (no es thread-safe: cada connection solo se puede usar desde el hilo que
    la creo) y su propio httpx.Client, prefetch_count=1 -- nunca tiene mas de
    1 mensaje sin confirmar a la vez."""
    connection, channel = _connect()
    channel.basic_qos(prefetch_count=1)
    client = httpx.Client(timeout=HTTP_TIMEOUT)

    def on_message(ch, method_frame, header_frame, body):
        n = in_flight.incr()
        client.get(url)  # la llamada lenta -- el mensaje sigue unacked mientras dura
        in_flight.decr()
        ch.basic_ack(delivery_tag=method_frame.delivery_tag)  # acks_late: recien aca
        procesados.append(body.decode())
        print(f"  [worker-{worker_id}] proceso {body.decode()!r} (in_flight llego a {n})")

    channel.basic_consume(queue=QUEUE_NAME, on_message_callback=on_message)

    # Loop manual (en vez de start_consuming) para poder parar cuando ya se
    # proceso todo lo esperado, sin bloquear para siempre.
    while time.monotonic() < deadline:
        if len(procesados) >= total_esperado:
            break
        connection.process_data_events(time_limit=0.2)

    client.close()
    connection.close()


def _run_escenario(nombre, worker_concurrency, url):
    print(f"=== {nombre}: WORKER_CONCURRENCY={worker_concurrency} ===")
    _purge()
    in_flight = InFlight()
    procesados = []
    deadline = time.monotonic() + N_MESSAGES * SLEEP_SECONDS + 15

    workers = [
        threading.Thread(
            target=_worker,
            args=(i + 1, url, in_flight, procesados, N_MESSAGES, deadline),
        )
        for i in range(worker_concurrency)
    ]
    for w in workers:
        w.start()
    time.sleep(0.5)  # asegurar que todos ya esten suscritos con su prefetch aplicado

    _publish(N_MESSAGES)

    # Connection propia, solo para consultar cuantos mensajes quedan "Ready"
    # en la cola (queue_declare(passive=True)) -- no cuenta los unacked que
    # ya tiene algun worker en mano, esos ya no son "queued".
    monitor_connection, monitor_channel = _connect()
    inicio = time.monotonic()
    last_print = -1.0
    while len(procesados) < N_MESSAGES and time.monotonic() < deadline:
        ready = monitor_channel.queue_declare(queue=QUEUE_NAME, passive=True).method.message_count
        elapsed = time.monotonic() - inicio
        if elapsed - last_print >= 0.3:
            print(
                f"    t={elapsed:5.1f}s  queued(ready)={ready:2d}  "
                f"in_flight={in_flight.value}/{worker_concurrency}  "
                f"procesados={len(procesados):2d}/{N_MESSAGES}"
            )
            last_print = elapsed
        time.sleep(0.1)
    monitor_connection.close()

    for w in workers:
        w.join()

    print(f"  max in_flight observado: {in_flight.max_seen}")
    assert len(procesados) == N_MESSAGES, (
        f"se esperaban {N_MESSAGES} procesados, salieron {len(procesados)}"
    )
    assert in_flight.max_seen == worker_concurrency, (
        f"se esperaba que in_flight llegara a {worker_concurrency}, "
        f"llego a {in_flight.max_seen}"
    )
    print()


def main():
    server = start_server()
    port = server.server_address[1]
    url = f"http://127.0.0.1:{port}/"
    print(f"Downstream propio arriba en {url} (duerme {SLEEP_SECONDS}s por request).\n")

    _run_escenario("Escenario A", WORKER_CONCURRENCY_A, url)
    print(
        f"Confirmado: con WORKER_CONCURRENCY={WORKER_CONCURRENCY_A}, in_flight nunca "
        f"pasa de {WORKER_CONCURRENCY_A} -- los demas mensajes esperan su turno en la "
        f"cola (Ready), de a uno, aunque el downstream pudiera atender varios en "
        f"paralelo.\n"
    )

    _run_escenario("Escenario B", WORKER_CONCURRENCY_B, url)
    print(
        f"Confirmado: con WORKER_CONCURRENCY={WORKER_CONCURRENCY_B}, in_flight sube "
        f"hasta {WORKER_CONCURRENCY_B} y se mantiene ahi -- 'queued sube, in_flight "
        f"tope en N, queued baja de a N', el mecanismo real de la congestion, "
        f"reconstruido con basic_qos(prefetch_count=1) x{WORKER_CONCURRENCY_B} + ack "
        f"manual + un cliente HTTP con timeout partido -- sin Celery ni Postgres de "
        f"por medio."
    )

    server.shutdown()


if __name__ == "__main__":
    main()
